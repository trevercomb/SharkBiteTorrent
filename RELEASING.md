# Releasing

Changes go to `main` as they're made (each user-visible one noted under **Unreleased** in [`CHANGELOG.md`](CHANGELOG.md)). A release is cut only when the maintainer decides to ship. Every push already runs [Checks](.github/workflows/checks.yml) (tests, type checks, govulncheck, npm audit) and [CodeQL](.github/workflows/codeql.yml); the Release workflow runs govulncheck and npm audit again and won't publish if they fail.

## Before tagging

1. **Checks and CodeQL are green** on the commit being released, and **Security → Code scanning** has no open alerts (fix them, or dismiss them with a written reason).
2. **Leak test (engine)**, on Windows, from an **administrator** terminal (it turns on Windows' connection and DNS auditing for the run and restores the previous settings afterwards):
   ```sh
   go run ./cmd/leakcheck -selftest path/to/legal.torrent    # must print "selftest OK" (it caught the planted leaks)
   go run ./cmd/leakcheck -seconds 60 path/to/legal.torrent  # must PASS (INCONCLUSIVE: it barely downloaded; run again)
   ```
   Every connection the OS sees from the process and everything it starts is checked (Windows Filtering Platform events 5156/5157, process creation 4688), however short, plus every lookup through the system DNS resolver (DNS Client event 3006). UDP is only allowed from the main process to the VPN server. A run whose own test connection or tunnel traffic isn't recorded fails instead of passing.
   **On Linux** (any user with sudo; it asks for the password once): the same two commands, run normally (not with sudo). The watched process runs in its own cgroup and nftables counts every packet it and its children send; system DNS lookups are turned into countable DNS packets with a private nsswitch.conf (and nscd is hidden from it). It removes its nftables table afterwards. Differences from Windows: UDP to the VPN server is allowed from any of the watched processes, not only the main one; and work other processes do for the app outside its cgroup (D-Bus calls to systemd-resolved, desktop portals) isn't seen.
   **On macOS** (an admin user; sudo asks for the password once): the same two commands, run normally. `tcpdump -i pktap,all` tags each packet with the process that sent it. macOS leaves some packets untagged (often a connection's outgoing ones, while tagging its replies), so an untagged (or kernel-tagged) packet counts as the app's if another packet of its connection was tagged with the app, or if it was sent from a port one of the app's processes had open (`lsof`, every second); TCP/UDP like that which nothing claims fails the run (`-allow-untagged` passes it once you've seen it was another program's), except the kernel's own network-drive traffic (SMB, NFS, AFP to the home network), which is counted apart. System DNS lookups are judged from mDNSResponder's log, which names the client process (Network.framework's lookups, which WebKit makes, included; the selftest makes one with `nscurl`); it hides the names but gives a hash of each, and the check learns the hashes of the allowed names (the VPN accounts' sign-in hosts) by looking them up itself first. A VPN account's documented calls are only allowed from the app's main process while it connects, and a VPN server only counts if the app sent it a WireGuard handshake. Limits: processes are listed once a second, so a program the app starts that sends and exits in between isn't known to be the app's: one named like a program the app starts (`open`, `clamscan`, the update's `ditto`/`plutil`/`codesign`/`sh`) counts as the app's, and any other that sent packets off the computer is listed for you to look at. Work system services do in their own name isn't attributed: the run lists what trustd, ocspd, syspolicyd and nsurlsessiond sent, which may be any program's (the app checks certificates itself, so trustd shouldn't do anything for it). And a documented call is judged by where it goes: HTTPS to an address DNS gave for a sign-in host passes whatever site it asks for there, which matters only if that host shares its addresses (a CDN).
3. **Leak test (real app)**: install the build, **quit it** (any VPN choice works: with a VPN account, the check reads the server the app connected to afterwards), then from an administrator terminal run `go run ./cmd/leakcheck -app`. It launches the app itself (so startup is covered) and watches it for 150 s. The person running it follows the steps it prints: leave the window alone for the first minute, then search and add a result, type in the magnet box, open every Settings section, turn on the search proxy and click Check it's working, switch VPN provider and back (reconnecting), check for updates, and paste `https://example.com/` in Paste links (its browser window opens; let the page load, then close it). If the remote control is on, also use it from a phone on the home Wi-Fi during the run (incoming home-network connections to its port are allowed; nothing else is). Must PASS.
   **On Linux**: build or install the app, quit it, then run `go run ./cmd/leakcheck -app` (it launches `/usr/bin/sharkbitetorrent`; use `-exe build/bin/SharkBiteTorrent` for a local build). Same steps as above; at the end it asks you to quit the app from the tray, so shutdown is covered too. Start the app normally afterwards: the copy it launched used a private DNS setup.
   **On macOS**: quit the app (Cmd+Q), then run `go run ./cmd/leakcheck -app` (it opens `/Applications/SharkBiteTorrent.app` the way Finder does; use `-exe build/bin/SharkBiteTorrent.app` for a local build). Same steps; at the end it asks you to quit with Cmd+Q. It must find the app's WebKit processes (through `launchctl procinfo`), or it fails. Don't run the engine test while Prowlarr is set to use the app's search proxy and the app is closed: Prowlarr's searches then fail, and it ignores its sites for a while afterwards, so the next searches find nothing.
4. **Fresh-eyes audit of the changes**: a reviewer that hasn't seen the work (a new Claude session or agent, or a person) reviews `git diff <last-tag>..HEAD` with the brief below. Its report goes to the maintainer unedited. Required when the release touches networking, the VPN/tunnel, the updater, signing, the installer, secrets or file handling; otherwise every few releases. Every few releases, audit the whole repository instead of the diff.
5. **Library updates**: run `scripts/outdated.sh`. Update `golang.org/x/crypto/x509roots/fallback` (the trusted root certificates the app checks TLS against; see `roots.go`) for every release, to a commit at least 7 days old, since Dependabot doesn't follow it (it has no version tags). It lists the libraries (Go, npm, the Go toolchain, wails, go-webview2) that have newer versions; it's a report, not a gate. For each one, read what the new version changes and decide: update now (and test), or leave it for later with a reason. Dependabot opens weekly pull requests for most of these (`.github/dependabot.yml`, each update at least 7 days old); wails (with `WAILS_VERSION` in the workflows) and the patched go-webview2 are updated by hand. Known vulnerabilities don't wait for this: govulncheck and npm audit block every push, and the release itself.
6. **CHANGELOG**: rename **Unreleased** to `## [x.y.z] - YYYY-MM-DD` and make sure it says what users will notice.

## Shipping

```sh
# bump wails.json productVersion and packaging/arch/PKGBUILD _version, commit
git tag -a vX.Y.Z -m "Shark BiteTorrent X.Y.Z" && git push origin vX.Y.Z
# wait for the Release workflow (creates a draft), then on the maintainer's computer:
git checkout vX.Y.Z                     # publish refuses anything but a clean checkout of the tag
go run ./cmd/releasekey publish vX.Y.Z   # asks for the key's password; checks build provenance + hashes, signs, publishes
git checkout main
```

Check the draft's release notes before publishing.

`publish` also downloads the Microsoft Store package (`.msix`) from that release run, checks its build provenance the same way (nothing is published if it fails), and puts it in your Downloads folder. Upload that file in Partner Center: the app → **Packages** → drag it in → **Submit**. (Store API automation isn't available on individual developer accounts; and keeping the upload on the maintainer's computer means a hijacked GitHub account can't push a Store update either.)

## Betas

A beta (`vX.Y.Z-beta.N`, the version of the next release) ships what's committed on `main` to people on the **Beta** update channel, without waiting for a release. It's tagged, built and signed exactly like a release, with lighter checks:

1. Checks and CodeQL green on the commit; the **Unreleased** section of `CHANGELOG.md` says what's new (it becomes the beta's notes, so don't rename it).
2. The engine leak test if networking, the VPN or the updater changed. No audit: betas aren't audited; the audit (step 4) comes before the stable release and covers everything since the last one.
3. Tag and publish as in Shipping, without bumping any version (the workflow takes it from the tag):
   ```sh
   git tag -a vX.Y.Z-beta.N -m "Shark BiteTorrent X.Y.Z beta N" && git push origin vX.Y.Z-beta.N
   git checkout vX.Y.Z-beta.N && go run ./cmd/releasekey publish vX.Y.Z-beta.N && git checkout main
   ```
   It's published as a pre-release, so `/releases/latest` (what Stable checks) doesn't move. There's no Store package for a beta.

The app on the Beta channel finds betas through the releases feed (`/releases.atom`, the newest 10 releases), so a beta older than the 10 newest releases isn't offered. The feed also lists tags that have no published release (a beta's tag while CI builds it, until it's published, or an abandoned one), so the app offers a beta only once its `SHA256SUMS.txt.minisig` can be downloaded. That's fine: a newer beta or release always is.

## Audit brief

To run it through the API instead of interactively: Actions → **Audit** → Run workflow (optionally with extra instructions). It sends the source and the diff since the last tag to Claude in one request (`scripts/audit.py`, about $1–3 a run; `python scripts/audit.py --dry-run` shows the size without sending anything) and attaches the report to the run as `audit-report`. It needs the `ANTHROPIC_API_KEY` repository secret, from a Console account with auto-reload off. **The repository is public, so anyone signed in to GitHub can download a run's artifacts:** the report is kept for one day only, and should be deleted as soon as it's downloaded (`gh run download <run> -n audit-report`, then `gh api -X DELETE repos/trevercomb/SharkBiteTorrent/actions/artifacts/<id>`, the ID from `gh api repos/trevercomb/SharkBiteTorrent/actions/runs/<run>/artifacts`). Don't put anything secret in its extra instructions: they show in the run's public log.

> You are auditing Shark BiteTorrent, a BitTorrent client whose core promise is that only this app's traffic uses a VPN, and that nothing (torrents, DNS, trackers, search, updates, provider APIs) leaks outside it unless the user explicitly chose "No VPN". Review `git diff <last-tag>..HEAD` (or the whole repository if asked). Look for: traffic that can leave outside the tunnel; secrets (keys, passwords, API keys) that could be logged, shown or sent somewhere; files read, written or deleted outside where they should be; anything that runs other programs; weaknesses in the updater, signing or installer; supply-chain risks in dependencies and workflows; and claims in README.md, PRIVACY.md or the app's text that the code doesn't back up. Assume the author missed things. For each finding give the file and line, what goes wrong in a concrete scenario, and a suggested fix. Say plainly when you found nothing in an area, and what you didn't review.
